# Monthly Search Console feedback loop

The verification tag is already in the site. This is a monthly content review,
not an indexing campaign.

## Once a month

1. **Performance → Search results → Export.**
   - Date range: the last 28 days (or the last 3 months for a quarterly view).
   - Tabs: Queries, Pages. Export each as CSV.
2. **Run the review helper.**
   ```bash
   node tools/search-console-review.mjs --file queries.csv
   node tools/search-console-review.mjs --file queries.csv --json > review.json
   ```
   It surfaces high-impression/low-CTR queries, striking-distance queries
   (positions 5–20) and country/office terms.
3. **Compare the query wording with the page.**
   - Does the title, H1 and first paragraph answer the query in the same words?
   - Is the page the right office/country page, or should it link to one?
   - Is the page's snippet being rewritten because the description is vague?
   - For a report-date query, does a dated `/reports/...` page exist?
4. **Check Pages → Indexing.**
   - Confirm the six office pages are indexed.
   - Look for 404s, soft 404s and “Crawled – currently not indexed”.
   - A page that is not indexed yet does not need a mass indexing request.
5. **Make one meaningful change per page.** Update copy, a title, an internal
   link or a missing dated report. Rebuild, run the link and accessibility
   checks, then deploy.
6. **Only after the change**, use URL Inspection for that URL and request
   indexing if it is appropriate. Do not use URL Inspection as a batch tool,
   and do not request indexing for pages you did not change.

## Technical health (monthly or after a cutover)

- **Sitemaps:** keep the index at
  `https://irishvisaupdatetracker.pages.dev/sitemap.xml` (or the custom-domain
  equivalent) and its four children in Search Console — the children give
  per-family diagnostics, the index is what `robots.txt` names. `/sitemap` is
  not a sitemap and should not be submitted. The sitemap is generated by the build and
  the live file contained 127 URLs when checked on 25 November 2026. Search
  Console’s sitemap count can lag the live XML after a deploy or recrawl; confirm
  the URL count in the live `sitemap.xml` before treating a lower GSC number as
  missing pages. A “couldn't fetch” status on the shared `pages.dev` host is a
  reason to move to the custom domain, not to resubmit the same URL.
- **Page indexing:** compare the sitemap count with the indexed count. A page
  that is excluded because it is new, thin or `noindex` is not automatically a
  defect; check its purpose before changing it. `/community-timelines` is
  intentionally `noindex, follow` until its aggregates clear the minimum sample.
- **Core Web Vitals:** use the GSC report for field data when enough traffic
  exists, and PageSpeed Insights/CrUX for a lab cross-check. The current lab
  baseline is recorded in `perf/BASELINE.md`. Do not rebuild the bundle for a
  single lab run; verify field data first.
- **Custom domain:** after cutover, submit the new sitemap, keep the old
  property verified, and use Settings → Change of address. Do not request
  indexing for the whole sitemap to force a domain move.
- **Bing:** the property is verified and `sitemap.xml` is submitted in Bing
  Webmaster Tools. On 25 November 2026 the refreshed feed reported Success with
  127 URLs. Let IndexNow announce changed URLs; do not resubmit the sitemap for
  each content change.

## What not to do

- Do not mass-request indexing or submit the same URL repeatedly.
- Do not create city doorway pages for country queries. Extend the existing
  office page, which already carries the country scope.
- Do not change a title only to chase a query if the page does not answer it.
- Do not treat impressions as demand for a new page; check whether the
  existing page is simply unclear.

## Bing and IndexNow

Google ignores IndexNow; Bing, Copilot and Yandex use it. The deploy workflow
runs `tools/indexnow.mjs --send --changed` after a successful deploy, using the
public key file `5ba7cee4d0b7816bb7950443892c3b7d.txt`. The set covers home,
status, reports, monthly report, open data, the six office pages, Help, Daily
summaries and the today page; it is rebuilt from the latest data and generated
HTML, so removed pages are never announced.

`--changed` fingerprints each built HTML page and compares it with
`.cache/indexnow-state.json`. The fingerprint ignores asset-version query
strings and generated check/build timestamps, so an ordinary rebuild with no
content change submits nothing. New report permalinks, changed report pages and
edited priority pages are submitted once; the workflow caches the state file
between deploys. A first run with no state (or a deleted state file) submits the
current set once, which is the intended baseline. The 25 November 2026 baseline
is also checked in as `.indexnow-state.json`; the workflow copies it into an
empty cache so a cold cache does not resend all 120 URLs. `--send` without
`--changed` still forces the full set for recovery. Dry-run it locally after
`npm run build`:

```bash
node tools/indexnow.mjs --dry-run --changed
```

The deploy workflow does this automatically. For a deliberate one-off subset,
combine `--only` with the normal state-backed run:

```bash
node tools/indexnow.mjs --send --only=irish-visa-decisions-today,help
```

`--only` accepts route paths, `.html` names or absolute URLs and intersects
them with the generated set, so a path that is not public is never announced.
It composes with `--changed`, which is useful for a targeted post-deploy check.

The working state file lives under `.cache/` and is gitignored. The deploy
workflow caches it and falls back to the checked-in `.indexnow-state.json`
baseline when the cache is empty. Both files store only the URL-to-fingerprint
map; no secrets or page content are kept. Delete the cache only when you
deliberately want to resubmit the full current set.

The property is verified and `https://irishvisaupdatetracker.pages.dev/sitemap.xml`
is already submitted, so do not resubmit it for each content change. Let the
post-deploy `--changed` step announce later changes. Never run the live IndexNow
command without a deploy authorisation.

## Bot access audit

Run the live probe after a deploy, or when a crawler reports a fetch error:

```bash
npm run audit:bots
npm run audit:bots -- --json
```

It sends Googlebot, Bingbot and YandexBot user agents to the homepage, sitemap,
robots.txt, today page, VFS page, all-pages index and the IndexNow key. It fails
on a non-200 status, a `cf-mitigated` challenge, an HTML challenge page, a wrong
content type, a malformed sitemap, a missing robots sitemap line or a key-body
mismatch. A passing run proves the origin and Cloudflare edge are serving those
paths to that user agent at that moment; it does not replace the Cloudflare
firewall/bot-management event log, which needs dashboard access.

## Refresh the weekly scorecard

The dashboard is generated from `data/search-coverage.json`. Each source is
measured independently: Search Console (Search Analytics, URL Inspection,
sitemaps), Bing Webmaster crawl stats and Cloudflare Web Analytics (RUM
traffic and Core Web Vitals). A source whose credential is missing keeps the
previously committed section and adds a warning, so a run with only one
credential still produces a fresh snapshot. Credentials come from the
environment, then from the gitignored `.dev.vars`/`.env`; `--sources=gsc,bing,cloudflare`
restricts a run and `--days=N` sets the Cloudflare RUM window (default 28).

The cross-engine `indexing_scorecard` object is a small manual
snapshot because Bing does not expose an indexed count and Yandex has no
property yet:

1. Replace `indexing_scorecard.checked_at` and `next_check` (one week later).
2. Refresh the Google and Bing inspection sample. Record `Unknown` or
   `Not exposed` rather than turning a missing API field into zero.
3. Count submitted URLs from the live `sitemap.xml`, not from an old seed.
4. Run `node tools/coverage-dashboard.mjs`; it preserves the scorecard and
   re-renders `/search-coverage`.
5. Commit the JSON and HTML with the weekly snapshot. Do not mark the page
   indexable; it is an operations page (`noindex, follow`).

| File | Contents |
| --- | --- |
| `/sitemap-pages.xml` | trust, guide, data and tool pages |
| `/sitemap-offices.xml` | the six office pages and their report indexes |
| `/sitemap-reports.xml` | dated report permalinks |
| `/sitemap-decisions.xml` | `/decisions`, date pages and monthly archives |

robots.txt still names `/sitemap.xml`; a sitemap index is a valid target. In
Search Console, submit the index once, then read **Sitemaps → the child file**
for the family you care about. Bing Webmaster shows the same split under
Sitemaps.

Why it matters: 130 URLs in one file make "office pages indexed, report
permalinks ignored" invisible. With the split, the family totals are the
diagnostic. It does not by itself make Google crawl anything; links and content
do that.

The build refuses to finish if a child sitemap is missing
(`tools/audit-discovery.mjs`), and `npm run audit:bots` fetches every child so a
wrong content type or a 404 is caught before it reaches an index.

## Measure the crawl after a change

1. Use URL Inspection for the one URL that changed. Record its coverage state
   and canonical; do not inspect a batch.
2. Open Crawl Stats and check that Googlebot is fetching the new path, not only
   the homepage. A new path can take days to appear.
3. Track the indexed count weekly. Do not resubmit the sitemap or request
   indexing again while a URL is already queued or indexed.
4. Compare the Pages and Queries exports: if Google still associates “today”
   with the homepage after the today page is indexed, adjust the internal anchor
   or the page copy — not the indexing tools.
5. After a deploy, confirm the sitemap lastmod for the changed office pages is
   the content revision date (the build uses `data/content-dates.json`), not the
   older report date.

## Crawl recency comes first

Before reading queries, inspect the homepage and read `lastCrawlTime`. On
25 November 2026 it was **7 November** — 18 days earlier — while Bing was
crawling the same page daily. That single field explained every other symptom:
the office pages were unknown, the today page was unknown, and the impressions
gaining ground came from the 7 November snapshot rather than from the new work.

- `lastCrawlTime` inside 48 hours: Google is looking. Diagnose content.
- Older than 7 days: Google is not looking. Nothing in the markup, sitemap or
  internal links will change that. The work is demand: the manual
  `Request indexing` for the eight priority URLs, one or two real external
  citations, and time.
- Older than 14 days with no movement after a sitemap resubmission: check
  Cloudflare's verified-bot handling on the zone and confirm Googlebot fetches
  are not being challenged, then move to the custom domain. The shared
  `pages.dev` host is not a reason to keep resubmitting the same sitemap.

A crawl gap also means a content experiment cannot start: there is no new
snapshot to test. Record the date in `data/search-baseline.json` whenever it is
read, so a later review can tell a slow crawl from a fast one.

## CTR experiment protocol

2.7% CTR at position 9–11 is the largest visible loss in the account. Change one
page at a time, and only once that page is indexed and its position has been
stable for a week:

1. Record the page's 14-day clicks, impressions, CTR and average position.
2. Change **one** title or description. Keep the H1, URL, canonical and content
   unchanged, so the only variable is the snippet.
3. Wait 14 days. Compare the same window length, not a longer one that flatters
   the result.
4. Keep the change only if CTR improves without average position dropping by
   more than 2 places. A title that wins clicks on a lower ranking is a loss.
5. Record the before/after block next to `data/search-baseline.json`.

Do not run two experiments on the same page at once, and do not change a title
before the page is indexed — there is nothing to measure yet.
